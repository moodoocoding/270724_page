# AI 원데이 클래스 보조 서비스 재설계 보고서

작성일: 2026-07-25  
검토 방식: 8개 전문 역할의 구조화된 AI 설계 검토, 100개 쟁점 토의  
검토 자료: 연수 표준안 PDF/PPTX, 1·2차시 활동지, 현재 Next.js/Supabase 서비스, `270725_webgame`

> 이 보고서의 “전문가 8인”은 실제 인간 자문단이 아니라 교육·제품·디자인·개발의 8개 전문 관점을 적용한 AI 검토 패널이다. 100회 토의는 100개의 독립 설계 쟁점에 대해 질문, 결론, 설계 영향을 기록하는 방식으로 진행했다.

### 토의 구성

| 회차 | 전문 관점 | 주요 쟁점 |
|---|---|---|
| 1~34 | 교육공학, 교사 연수 운영, 제품 전략 | 학습 목표, 차시별 경험, 산출물, 1차시 단순화 |
| 35~67 | UX 설계, 비주얼·타이포그래피, 접근성·반응형 | 화면 밀도, 글자, 여백, 내비게이션, 모바일 |
| 68~100 | 풀스택·데이터, 교육용 웹게임 | 3차시 게임 경험, 보안, 라이선스, Supabase, 운영 |

100개 쟁점에서 반복적으로 합의된 결론은 세 가지다.

- 네 차시는 같은 폼이 아니라 서로 다른 도구여야 한다.
- 화면을 꾸미기 전에 사용자의 현재 행동과 결과물을 먼저 보여야 한다.
- 복잡한 저장·보안·라이선스 처리는 사용자 화면이 아니라 시스템 뒤에서 해결해야 한다.

## 1. 결론

현재 서비스의 문제는 미적 취향보다 **서비스 모델이 잘못 잡힌 것**이다. 네 차시의 활동 성격이 다른데도 같은 제목, 미리보기, 입력 폼, 저장 버튼을 반복했다. 이 때문에 사용자는 연수 활동을 경험하는 대신 행정용 설문지를 작성하는 느낌을 받는다.

새 서비스는 “4개의 폼”이 아니라 다음 네 가지 전용 도구가 되어야 한다.

1. **1차시 - 관찰하고 판단을 수정하는 활동지**
2. **2차시 - AI 요청을 만들고 방법을 비교하는 프롬프트 워크벤치**
3. **3차시 - 교육용 게임을 직접 경험하고 변형하는 플레이 랩**
4. **4차시 - 동료 결과물을 사용하고 피드백하며 수정하는 갤러리 워크**

공통으로 유지할 것은 학교명·이름 입장, 자동 저장, 차시 이동, 제출 상태뿐이다.

## 2. 현재 서비스 진단

### 2.1 UX·UI

- 사용자가 지금 무엇을 해야 하는지보다 서비스 제목과 장식이 먼저 보인다.
- 전체 4차시와 1차시 내부 3단계가 탭으로 중첩되어 깊이가 과하다.
- 임시 저장과 다음 단계가 동시에 강조되어 주 행동이 불분명하다.
- 동일한 폼 구조가 모든 차시에 반복되어 차시별 학습 경험이 사라졌다.
- 넓은 화면에서도 실제 입력 영역은 좁고 바깥 여백은 지나치게 크다.

### 2.2 타이포그래피

- 화면 제목이 활동 제목보다 과도하게 크다.
- 10~11px 보조문구는 연수장, 노트북, 프로젝터 환경에서 작다.
- 한국어 폰트를 선언했지만 실제 폰트 파일을 제공하지 않아 기기별 차이가 발생한다.
- 필요한 위계보다 굵기와 크기 대비가 강해 화면이 포트폴리오처럼 보인다.

### 2.3 구조

- 현재 구조는 “콘텐츠를 담는 범용 폼”에 가깝다.
- 1차시는 개념 확인, 분류, 정보 탐색, 판단 수정이 핵심이다.
- 2차시는 AI에 전달할 맥락을 조립하고 결과를 비교·선택하는 것이 핵심이다.
- 3차시는 콘텐츠의 작동 원리를 직접 경험하고 제작·변형하는 것이 핵심이다.
- 4차시는 다른 사람의 콘텐츠를 실제 사용하고 근거 있는 피드백을 남기는 것이 핵심이다.

## 3. 서비스 설계 원칙

1. **한 화면에는 한 가지 행동만 둔다.**
2. **입력 전에 반드시 경험이 있어야 한다.**
3. **차시별로 전용 작업 화면을 제공한다.**
4. **작성 내용은 자동 저장한다.**
5. **완료한 활동은 접어서 화면 깊이를 줄인다.**
6. **설명은 한 문장, 예시는 필요할 때만 연다.**
7. **일반 텍스트는 최소 14px, 입력값은 16px로 한다.**
8. **작성 화면 폭은 720~800px, 게임·비교 화면만 최대 1040px를 사용한다.**
9. **주 버튼은 화면당 하나만 둔다.**
10. **장식보다 상태, 다음 행동, 결과물을 우선한다.**

```text

워크북

 │   ├─ 추가 정보로 판단 수정
 │   └─ 수업 문제 한 문장 완성
 ├─ 2차시 AI와 방법 탐색
 │   ├─ 1차시 결과 확인

 │   ├─ AI 실행
 │   └─ 방법 비교·선택
 ├─ 3차시 게임 경험과 제작
 │   ├─ 추천 게임 선택
 │   ├─ 3분 체험
 │   ├─ 작동 원리 분석
 │   └─ 변형 계획 및 결과 제출
 └─ 4차시 갤러리 워크

     ├─ 네 관점 피드백
     └─ 수정 전후 및 최종 결과 제출
```

## 5. 차시별 서비스 제안

### 5.1 1차시 - 관찰과 문제 정의

목표: 학생에 대한 해석을 관찰 가능한 사실과 추가 정보로 다시 보고, 교사가 바꿀 수 있는 수업 조건을 한 문장으로 정한다.

권장 사용자 흐름:

1. 사실과 해석의 정의를 2열 비교표로 확인한다.
2. 네 문장을 사실/해석으로 선택하고 한 줄 피드백을 받는다.
3. 사례의 추가 정보 네 개를 한 장면씩 확인하며 처음 판단이 어떻게 바뀌는지 선택한다.
4. 자신의 수업에서는 확인할 행동·말·조건을 두 칸에 적는다.
5. 수업 문제 정의 문장을 완성한다.

간소화 방법:

- 세 개의 독립 탭을 없애고 하나의 세로 활동지로 만든다.
- 현재 활동만 펼치고 완료한 활동은 제목과 답만 남겨 접는다.
- 미래 활동은 제목만 예고한다.
- `임시 저장` 버튼을 없애고 자동 저장한다.
- 1·2번 활동은 한 화면에서 끝낸다.

최종 산출물:

> 처음에는 ___이라고 판단했다. 그러나 ___을 확인한 뒤, ___이 배움을 막았을 가능성이 있다고 보았다. 따라서 수업에서 ___을 해 볼 필요가 있다.

### 5.2 2차시 - AI 요청과 방법 탐색

목표: 1차시에서 정의한 문제를 AI가 이해할 수 있는 요청으로 바꾸고, 여러 방법 중 우리 수업에서 실행할 하나를 고른다.

권장 화면:

- 왼쪽 또는 상단: 1차시 최종 문장
- 중심: 학년·교과, 학생의 어려움, 원하는 활동, 수업 조건
- 오른쪽 또는 하단: 자동 조립된 프롬프트
- 실행 후: AI 제안 3개를 `배움 문제`, `실행 가능성`, `기존 수업 연결` 기준으로 비교

Gems 안내 자료 반영:

1. Gem 관리자에서 `새 Gem`을 연다.
2. 제공된 메타 프롬프트를 `요청 사항`에 붙여 넣는다.
3. 저장 후 `채팅 시작`으로 요청 초안을 완성형 프롬프트로 바꾼다.

보조 서비스는 Gemini 화면을 흉내 내지 않는다. 현재 해야 할 단계, 복사할 메타 프롬프트, 완료 확인 체크만 제공하고 실제 Gem 생성은 Gemini에서 수행한다.

중요한 변경:

- 현재처럼 AI 응답을 긴 textarea에 복사하지 않는다.
- 후보별 제목과 세 가지 평가만 입력한다.
- 메타 프롬프트 Gem 제작 안내와 완성형 프롬프트 복사를 실제 작업 흐름에 넣는다.

최종 산출물:

- 완성형 프롬프트
- 선택한 수업 방법
- 선택 이유 한 문장

### 5.3 3차시 - 교육용 게임 플레이 랩

목표: 완성된 웹게임을 학생의 입장에서 경험하고, 작동 원리를 분석한 뒤 자신의 수업에 맞는 변형 계획과 결과물을 만든다.

`270725_webgame` 조사 결과:

- README는 190개 이상을 설명한다.
- 현재 `single_html_games` 폴더에는 `index.html`을 포함해 HTML 100개가 있다.
- 원본 HTML 총량은 약 6.86MB이고 중앙값은 약 71.4KB다.
- 다수 게임이 Tailwind CDN, Google Fonts, FontAwesome, Chart.js, React UMD, Babel 등 외부 자원에 의존한다.
- localStorage, Analytics, `window.open`, `eval`, `getUserMedia`가 포함된 파일도 있어 전수 공개는 부적절하다.
- 라이선스는 CC BY-NC 4.0이며 KingsMath 출처 표시가 필수다.

첫 배포 범위:

- 전체 100개를 보여주지 않는다.
- 수학, 언어, 학급 도구, 전략/논리에서 6~12개만 선별한다.
- 3분 이내 이해, 전자칠판·모바일 적합성, 외부 의존성, 센서·추적 여부를 검수한다.

권장 사용자 흐름:

1. 추천 게임 하나를 고른다.
2. 격리된 화면에서 3분간 직접 체험한다.
3. 네 질문에 답한다.
   - 학생은 무엇을 하는가?
   - 어떤 피드백을 즉시 받는가?
   - 무엇이 반복 참여를 만드는가?
   - 수업 목표와 맞지 않는 부분은 무엇인가?
4. 유지할 것, 바꿀 것, 학생이 하게 될 일, 완료 기준을 정한다.
5. 결과 링크 또는 단일 HTML을 제출한다.

보안·운영 원칙:

- 게임은 워크북과 다른 origin에서 정적 호스팅한다.
- 검증 게임만 sandbox iframe으로 실행한다.
- 기본 권한은 `allow-scripts allow-pointer-lock`로 제한한다.
- Analytics와 불필요한 추적 코드는 제거한다.
- 사용자 HTML은 워크북 origin에서 직접 실행하지 않는다.
- 업로드는 정적 검사 후 격리 환경에서만 미리보기한다.
- 게임 화면과 참가자 변형 결과에 원작자, 원본 링크, 라이선스, 수정 여부를 표시한다.

최종 산출물:

- 선택한 게임과 체험 분석
- 게임 변형 계획
- 제작 결과 링크 또는 HTML
- 출처·라이선스·변경 내용

### 5.4 4차시 - 갤러리 워크와 수정

목표: 동료 콘텐츠를 학생의 관점에서 직접 사용하고, 구체적인 장면을 근거로 피드백한 뒤 실행 가능한 최종 결과물로 수정한다.

권장 사용자 흐름:

1. 동료 결과물 카드에서 하나를 선택한다.
2. 콘텐츠 제목, 수업 적용 문장, 해야 할 행동만 읽는다.
3. 결과물을 직접 사용한다.
4. 네 관점으로 피드백한다.
   - 배움에 도움이 되는가?
   - 활동 방법이 구체적인가?
   - 실제 시간·기기 환경에서 가능한가?
   - 내용·수준·개인정보·편향이 적절한가?
5. 가장 중요한 수정 한 가지를 선택한다.
6. 수정 전후와 최종 결과 링크를 제출한다.

중요한 변경:

- 현재의 `살릴 점`, `바꿀 점` textarea 두 개만으로 끝내지 않는다.
- 동료 결과물을 실제로 열고 사용한 뒤 피드백하도록 연결한다.
- 피드백은 작성자에게 익명 또는 이름 표시 방식 중 운영자가 선택하게 한다.
- 디자인 의견보다 오작동, 이해 어려움, 수준 부적합을 먼저 보게 한다.

## 7. 공통 UX

- 학교명과 이름으로 입장하되 서버가 무작위 세션 토큰을 발급한다.
- 입력 후 자동 저장하고 `저장됨 · 14:32`를 지속 표시한다.
- 주 행동은 `다음`, `선택 완료`, `제출` 중 하나만 강조한다.
- 제출 후에도 수정·재제출할 수 있다.
- 사이드바에는 차시명과 완료 상태만 둔다.
- 차시 내부 진행은 본문에 `1/3`처럼 표시한다.
- 모바일에서는 사이드바 대신 현재 차시 버튼과 목차 시트를 사용한다.
- 오류·완료는 색뿐 아니라 아이콘과 텍스트로 함께 표시한다.

## 8. 데이터·백엔드 제안

기존 `submissions.data_json`은 1·2·4차시의 초안 저장에 유지할 수 있다. 3차시 게임과 파일은 별도 테이블이 필요하다.

### games

`id`, `slug`, `title`, `subject`, `grade_band`, `summary`, `duration_min`, `source_url`, `hosted_url`, `license`, `attribution`, `launch_mode`, `sandbox_permissions`, `risk_level`, `review_status`, `content_hash`, `is_featured`

### game_experiences

`participant_id`, `submission_id`, `game_id`, `started_at`, `completed_at`, `analysis_json`

점수, 키 입력, 플레이 경로는 수집하지 않는다.

### artifacts

`participant_id`, `submission_id`, `kind`, `url`, `storage_path`, `mime_type`, `size_bytes`, `content_hash`, `scan_status`, `created_at`

### 보안

- Service Role Key는 Next.js 서버에서만 사용한다.
- participantId만으로 소유권을 판단하지 않는다.
- 참가 등록 시 세션 토큰을 발급하고 API에서 검증한다.
- 업로드 HTML은 UTF-8 단일 파일, 초기 2MB 이하로 제한한다.
- 서버가 임의 제출 URL을 가져오지 않는다.

## 9. 강사 화면

강사 화면의 목적은 원문을 모두 읽는 것이 아니라 막힌 참가자를 빠르게 찾는 것이다.

표시 상태:

- 미시작
- 활동 중
- 결과 작성
- 제출 완료
- 검토 필요

추가 기능:

- 차시별 진행 인원
- 2차시 선택 방법 분포
- 3차시 선택 게임 분포와 체험 완료 상태
- 4차시 피드백 미수신 참가자
- 참가자 선택 시 전체 결과 보기

## 10. 구현 우선순위

### 1단계 - UX 골격 재구성

- 공통 셸과 차시별 화면 분리
- 자동 저장
- 타이포그래피·폭·간격 정상화
- 1차시를 연속 활동지로 단순화

### 2단계 - 2차시 워크벤치

- 1차시 결과 불러오기
- 프롬프트 조립·복사
- AI 방법 후보 비교·선택

### 3단계 - 3차시 플레이 랩

- 연수용 게임 6~12개 선정·검수
- 별도 origin 호스팅과 sandbox
- 체험·분석·변형 계획
- 결과 링크 제출

### 4단계 - 파일과 갤러리 워크

- 안전한 HTML 업로드
- 동료 결과물 배정·사용
- 피드백과 수정 전후 비교

### 5단계 - 운영 안정화

- 세션 토큰
- 강사 대시보드
- 게임 manifest와 변경 재검토
- 접근성·학교망·전자칠판·모바일 검증

## 11. 삭제하거나 금지할 것

- 네 차시에 동일한 범용 폼 적용
- 의미 없는 그라디언트, 블러, 장식용 메모
- 12px 미만의 일반 텍스트
- 모든 요소의 굵은 글씨
- 카드마다 다른 둥근 모서리와 그림자
- 한 화면에 두 개 이상의 주 버튼
- 수동 임시 저장을 반복하게 하는 구조
- 탭 안에 카드, 카드 안에 다시 미리보기와 폼을 넣는 구조
- 게임 100개를 검수 없이 같은 origin에서 실행
- 참가자 HTML을 즉시 실행
- 게임 점수·키 입력 등 불필요한 행동 데이터 수집

## 12. 성공 기준

- 참가자가 설명 없이 10초 안에 현재 할 일을 말할 수 있다.
- 1차시 첫 두 활동을 페이지 이동 없이 완료할 수 있다.
- 화면당 주 버튼은 하나다.
- 모든 일반 텍스트는 14px 이상이다.
- 1366×768에서 핵심 활동과 다음 버튼이 동시에 보인다.
- 모바일 360px에서 가로 스크롤 없이 작성할 수 있다.
- 차시별 화면을 제목 없이 보아도 서로 다른 활동임을 구분할 수 있다.
- 3차시 게임은 8초 안에 실행되거나 대체 실행 방법을 안내한다.
- 참가자 업로드 HTML은 워크북 origin에서 실행되지 않는다.
- 모든 게임과 변형 결과에 출처와 라이선스가 표시된다.
